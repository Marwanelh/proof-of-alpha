## Axis 6 spec (registry.ts)

`server/registry.ts` should begin with `import "server-only"` and export one narrow function:

`recordCallReferenced(input: RecordCallInput, deps: { publicClient; walletClient; account; registry }): Promise<OnChainReceipt>`.

The private key must remain outside this function; pass a configured viem wallet client/account, never a key string. Use one minimal ABI containing `readsFeed()`, `recordCallReferenced(...)`, and `CallRecorded`.

Before encoding, it must validate:

- The public and wallet clients are on chain 97, agree on chain ID, and `registry` is a valid non-zero address.
- `readsFeed()` is exactly `false`; otherwise this is not a referenced deployment.
- `originalText` and `authorId` are non-empty; compute `postHash` and `kolId` with viem `keccak256(toBytes(...))`.
- `asset` is uppercase ASCII, 1–4 UTF-8 bytes, and encoded as a right-padded `bytes4`.
- Direction maps only `bullish → 1` and `bearish → -1`.
- `cournot.probability` is finite and in `[0,1]`; round once to basis points, require `0..10000`, then pass `uint16`.
- `deadline` is a valid ISO instant, strictly after `postedAt` and the recording time, integral seconds, and within `uint64`.
- CMC and target prices match a strict positive decimal grammar. Scale with viem `parseUnits` using `atlas.decimals`; reject excess fractional precision rather than silently rounding. Never multiply JavaScript floats.
- `atlas.decimals` is an integer in the provider’s valid width.
- `atlas.price` is decimal digits only, positive and within `uint80` as the provider type—and consequently within the contract’s `uint128`.
- `atlas.onchainTs` is positive and within `uint48`; `mainnetBlock` is positive and within `uint64`.
- The Atlas address/feed ID and referenced block came from the normalized snapshot; do not accept a caller-supplied `atlasVerified`.

Then:

1. Call `publicClient.simulateContract` with `recordCallReferenced`.
2. Submit exactly the simulated request through `walletClient.writeContract`.
3. Call `waitForTransactionReceipt({ hash, confirmations: 1 })`.
4. Explicitly require `receipt.status === "success"`.
5. Decode `CallRecorded` only from logs emitted by the configured registry. Require exactly one matching event, matching hashes/asset/direction/deadline/bps/prices, and `atlasVerified === false`.
6. Return the mined hash, decoded event ID, chain 97, registry address and a literal `atlasVerified: false`.

If simulation or mining reverts, throw a typed `RegistryError` preserving the cause and transaction hash when available. Return no `OnChainReceipt` and let `verify()` fail.

It must never manufacture a receipt, return immediately from `writeContract`, infer success from a non-empty hash, call verified-mode `recordCall`, set `atlasVerified=true`, retry a reverted write as success, convert price integers through `Number`, log signer material, or accept a fixture/request ID as proof that Cournot was called.

## The one thing you disagree with us about

I disagree that server-side validation is sufficient for `CallRegistry`. It is a public contract, yet both recording functions accept semantically impossible probabilities, directions and deadlines from any caller. If the chain is meant to be the tamper-proof evidence layer, its cheap invariants must be enforced on-chain as well as in `registry.ts`.
